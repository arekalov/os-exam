## Camunda
**Camunda** — платформа для автоматизации бизнес-процессо (Workflow Automation), поддерживающая нотацию BPMN 2.0 для моделирования и исполнения процессов. Она предоставляет открытый движок (Java), средства для мониторинга и возможность оркестрации микросервисов, сочетая асинхронную обработку сообщений с долгоживущими бизнес-транзакциями.

## Особенности и возможности
* Поддержка основных элементов BPMN 2.0 из коробки: User Task, Service Task, подпроцессы, события-таймеры, сигналы, сообщения, компенсирующие события для Saga
* 2 архитектурные эпохи:
  * Camunda 7 работает как встраиваемая библиотека внутри вашего Java-приложения или как отдельный wildfly service.
  * Camunda 8, облачная, построена на горизонтально-масштабируемом движке Zeebe, использует протокол gRPC, концепцию «External Task» и хранит журнал событий в распределенном логе.
* Поддержка из коробки REST API вызовы, отправка/получение сообщений через JMS, Kafka, RabbitMQ, работа с электронной почтой, файловыми системами и JDBC-источниками данных, что позволяет связывать BPMN-процессы с внешними системами без написания Java-кода.

## Основные компоненты Camunda
* BPMN Engine — непосредственно движок, отвечающий за интерпретацию BPMN в объекты JAVA, сохранение объектов в базе и реализацию других вещей (типа листенеров активностей), которые крутятся вокруг процессов.
* Modeler — приложение для создания моделей BPMN процессов, нужных для других частей системы.
* Task list — веб-приложение, в котором исполнители выполняют задачи, поставленные на них бизнес-процессом, а также предоставляет исполнителям фильтрацию, сортировку, формы для заполнения данных, механизмы claim - захват задачи пользователем и assign - назначение в группу
* Cockpit - веб приложение для просмотра состояния процессов, показывает диаграмму процесса с наложенным «зеленым токеном», позволяет исправлять инциденты, обновлять версии процессов «на лету» и выполнять миграцию запущенных экземпляров на новую модель. 
* Admin - веб приложение для управления пользователями и правами доступа
* Optimize - (платное) приложение для анализа и оптимизации бизнес-процессов, строит дашборы, SLA-отчеты на основе истории выполненных процессов
* DMN Engine — аналог BPMN Engine для DMN.

## Установка и конфигурация Camunda
### Встроенная библиотека внутри приложения
Разрабатывается обычное Java-приложение, и в зависимостях указывается Camunda. БД своя, задачи свои, админка своя, исполнители свои. Удобнее для эксплуатации — следить нужно только за
одной базой и одной камундой, но создает проблему “шумных соседей” —
если кто-то из коллег сделает кривой процесс, то лягут все.

### Сервис внутри сервера приложений
Сервис внутри сервера приложений или контенейра серверлетов ("расшаренный" сервис), может использоваться другими приложениями, развернутыми в контейнере

### Standalone-сервер 
Развернуть Camunda как отдельно стоящий сервер, процессы при этом заливаются на него с помощью war-файлов, приложение(я) будут с ним контактировать по Rest API удаленно. БД, исполнители зада и админка общие. Обладает полной независиомтью, однако создает сложности в администрировании и управлении задачами

## Транзакции в Camunda
### 2 Phase-commit (2PC)

**2PC** - классический, тяжеловесный механизм распределенных транзакций, основанный на протоколе «все или ничего». Сначала управляющий сервис (координатор) опрашивает всех участников, готовы ли они выполнить операцию (фаза Prepare). Если все подтверждают готовность, координатор дает команду на фиксацию (Commit). Если хотя бы один ответил отказом — дается команда откатить изменения (Rollback). 2PC требует, чтобы все участники (сервисы, базы данных) поддерживали этот протокол и были доступны синхронно, что создает «блокировки» и резко снижает общую доступность (availability) системы, что критично для современных распределенных архитектур и микросервисов. Кроме того, многие современные NoSQL базы данных и брокеры сообщений просто не поддерживают 2PC. Как правило, 2PC используется для мгновенный транзакция (например в одной сети). Не актуален для Camunda 8, т.к. движок Zeebe является внешним по отношению к приложению, -> нет общей JTA-транзакции.

### Saga
Вместо глобальной блокировки, Saga разбивает длинную транзакцию на последовательность локальных,коротких шагов. Для каждого шага, который уже был выполнен, разработчик определяет компенсирующеедействие («откат»). Если на каком-то этапе произошла ошибка, запускается цепочка компенсаций,которая отменяет результаты всех ранее успешно выполненных шагов. Saga - основной способ обеспечения консистентности данных в распределенных системах на базе BPMN.
В Camunda механизм реализации - **Компенсирующие события** (Compensation Events), которые вешаются на каждый потенциально опасный шаг (Списать деньги) и содержат логику отметы (Вернуть деньги). Как правило, Saga используется для длительных транзакция, например, с участием внешних систем. Механизм поддерживается как в Camunda 7, так и в Camunda 8

![](images/14_saga.png)

### Поддержка JTA
**JTA (Java Transaction API)** — спецификация Java для управления распределёнными транзакциями, реализующая стандарт X/Open XA. Camunda 7 предоставляет интеграцию с JTA для работы в managed-средах Java EE/Spring-приложеней для использования в методах, где бизнес-логика и движок работают в общей транзакции:
* Автоматическое включение JDBC-операций движка в глобальную JTA-транзакцию
* Совместное использование транзакции между бизнес-логикой приложения и Camunda API
* Поддержка встроенных конфигураций для Wildfly, JBoss EAP, WebSphere, WebLogic

Camunda 8 не поддерживает JTA, т.к удаленный движок не участвует в Spring/JTA-транзакциях. Приложение делает REST-вызову к Zeebe, это отдельное сетевое взаимодействие, которое не может быть откачено вместо с SQL-операциями в БД

## Создание и изменение бизнес-процессов
Создание процессов в Camunda осуществляется в инструменте **Camunda Modeler** (десктопное или веб), где разработчик в графическом редакторе с помощью элементов BPMN 2.0 собирает диаграмму бизнес-процеcса, определяя его логику, задачи и потоки переходов. По завершении моделирования готовая диаграмма в формате BPMN 2.0 XML развертывается на движке Camunda, после чего процесс становится доступен для запуска новых экземпляров. Изменения вносятся в диаграмму процесса в Modeler, после чего новая версия модели деплоится на движок наряду с уже существующими версиями. Для применения новой логики к уже запущенным экземплярам процесса в Camunda предусмотрен механизм миграции (через Cockpit или API), позволяющий перенести выполняющиеся экземпляры со старой версии на новую, сохранив их текущее состояние.

## Cockpit
**Cockpit** — компонент Camunda, веб-приложение для мониторинга и оперативного управления процессами, предоставляющее операторам и администраторам полную видимость работающих и завершенных экземпляров процессов, включая их текущее состояние и визуальное отображение пути выполнения. Помимо отслеживания, Cockpit служит инструментом для исправления ошибок и управления инцидентами, позволяя находить зависшие или ошибочные экземпляры, анализировать причины сбоев и выполнять операции по их восстановлению (например, повторный запуск или удаление процессов). 

**Enterprise Cockpit** — расширенная версия Cockpit, содержащая в себе дополнительные функции: 
* развертывание описаний процессов
* перезапуск экземпляров процессов
* расширенный поиск по экземплярам процессов
* миграция экземпляров процессов между версиями.

## Modeler

**Modeler** - компонент Camunda в виде десктопного или веб-приложения для создания моделей бизнес-процессов, независим от других подсистем Camunda. На выходе получаем скомпилированный артефакт (.bpmn), который нужно подложить рантайму Camunda. Кроме BPMN-диаграм позволят создавать DMN-таблицы решений и Camunda Forms. Поддерживает совместную работу: комментрации и аннотации прямо на диаграмме, версионирование и запросы на ревью, синхронизацию с github. Также позволяет заводить шаблоны `Element Templates` для переиспользования настроек BPMN-элементов

### Использование внешних редакторов
Вместо Camunda Modeler можно использовать:
* bpmn.io/bpmn-js - бесплатный (ставит вотермарку) веб-заменить, используется как ядро в Camunda Modeler
* JointJS - платная библиотека для встраивания BPMN-моделлера в собственный продукт
* LudidChart -  облачный сервис для диаграмм, в том числе поддерживает BPMN
* ProcessMaker, Bonita BPM, Activiti, Signavio

## Роли и права доступа
### Концепция авторизации
Camunda 7 использует компонент авторизации (`Authorization`), встроенный непосредственно в движок, позволяющий гибко управлять доступом пользователей к различным ресурсам и операциям. Управление доступом осуществляется через API или админ-интерфейс Camunda. **Цель**: обеспечить безопасность на уровне отдельных экземпляров процессов, задач, определений процессов и других сущностей движка.

### Сущности
* **User** - Пользователь, физическое лицо, идентифицируемое по ID и паролю
* **Group** -	Группа пользователей, объединение для коллективного назначения прав
* **Tenant** - Арендатор, используется для изоляции данных в рамках одного экземпляра Camunda
* **Authorization** - Правило доступа, связывающее владельца, ресурс и набор разрешений
  
### Authorization
**Авторизация** — запись, определяющая, может ли владелец (пользователь/группа/tenant) выполнить определённое действие над определённым ресурсом, структура:
* Owner - id пользователя/группы, anyUser/anyGroup
* Resourse Type - к чему применяется правило (процесс/задача/решение/отчеты/пользователи и тд)
* Resource ID - конкретный экземпляр ресурса или *
* Permissions - набор разрешений для данного владельца на данный ресурс (например, READ, UPDATE, DELETE, CREATE, READ_HISTORY)

Есть 3 вида авторизаций:
* **GLOBAL** (`Resource ID = *`) - Действует на все ресурсы данного типа во всём движке, наименьший приоритет
* **GRANT** (конкретный Resource ID) - Предоставляет разрешения именно для этого конкретного ресурса, приоритет выше, чем у GLOBAL
* **REVOKE** (конкретный Resource ID) - Запрещает разрешения для конкретного ресурса, наивысший приоритет

### Управление авторизациями
1. Admin UI (веб-интерфейс Camunda) — ручное создание/редактирование
2. Java API — программное управление (`AuthorizationService, методы createNewAuthorization, set*, saveAuthorization`)
3. REST API — через HTTP-запросы

### Предопредереленные группы
* **camunda-admin** - полный доступ ко всем функциям и приложениям (Cockpit, Admin, Tasklist)
* **cockpit-users** - только мониторинг процессв в Cockpit
* **tasklist-users** - только работа с задачами в Tasklist
* **identity-users** - управление пользователями/группами в Admin
