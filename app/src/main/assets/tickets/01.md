**Java Message Service (JMS)** — стандарт Java API для создания, отправки, получения и чтения сообщений между компонентами распределенных приложений. Он обеспечивает асинхронную, слабосвязанную и надежную коммуникацию через очереди (point-to-point) или топики (publish/subscribe). Любой компонент, использующий JMS, прежде всего должен создать соединение с JMS провайдером

## Модели
Модель «**точка - точка**» (P2P) используется когда нужно чтобы сообщение отправлялось только 1 потребителю и характеризуется следующим:
* Каждое сообщение имеет только одного адресата
* Сообщение попадает в «очередь» (FIFO) адресата и может быть прочитано когда угодно. Если адресат не работал в момент отсылки сообщения, сообщение не пропадёт.
* После получения сообщения адресат посылает извещение.
* К одной очереди могут получить доступ несколько производителей, и читать могут несколько потребителей, однако любое сообщение на очереди может быть получено только одним потребителем, после чего удаляется из очереди

Модель «**издатель-подписчик**» (Pub-Sub) используется, когда нужно распределить сообщение по всем потребителям и характеризуется следующим:
* Подписчик подписывается на определённую «тему» (**topic**), могут подписывать на несколько
* Издатель публикует своё сообщение, которое получают все подписчики этой темы
* Получатель должен работать и быть подписан в момент отправки сообщения, т.е между издателем и подписчиком существует зависимость от времени
* Для счягчения строгой временной зависимости JMS поздволяет подписчикам создавать долговременную подписку, в таком случае даже если подписчик не активен, он может получать сообщения от издателя

## Сообщения JMS
JMS состоит из определенных сообщений и клиентов обменивающимися ими.
Сообщение состоит из трех частей: заголовок, свойств и тело.
* **Заголовок** – содержит информацию, которая используется для маршрутизации и идентификации сообщений (обязательный). Заголовок хранит мета информацию сообщения, заполняемую автоматически (JMSCorrelationID, JMSDeliveryMode, JMSDestination).
* **Свойство** – содержит информацию, которую можно использовать для фильтрации сообщений (время, дата и т. п.). Поле свойств схоже с заголовком, но оно заполняется программно, и позже получатель сможет прочитать эту информацию.
* **Тело** – содержит информацию о типе сообщения (определяется при создании сообщения) и полезную нагрузку.

## Распределенная обработка в JMS
**Распределенная обработка в JMS** — подход к построению систем обмена сообщениями, при котором несколько потребителей (consumers) работают с одной очередью (queue) или темой (topic) параллельно, обеспечивая горизонтальное масштабирование, отказоустойчивость и балансировку нагрузки.
* Спецификация API для обмена сообщениями в составе платформы Jakarta/Java EE.
* Широко используется при асинхронном выполнении задач.
* Позволяет инкапсулировать инфраструктурное ПО и протоколы обмена сообщениями за универсальным API. 
### Отправка сообщения:
* Лукапом из контекста получаем `ConnectionFactory`, с помощью которой создаём соединение Connection, с помощью которого создаём сессию Session.
* Лукапом из контекста вытаскиваем очередь по её имени (объект `Destination`).
* Создаём из полученной сессии producer, привязанный к очереди и отправляем сообщение: producer.send(message);
 
### Получение сообщения:
* Лукапом из контекста мы получаем `ConnectionFactory`, с помощью которой создаём соединение Connection, с помощью которого создаём сессию Session.
* Лукапом из контекста вытаскиваем очередь по её имени (объект `Destination`).
* Создаём из полученной сессии consumer, привязанный к очереди. Создаем объект MessageListener и сетим его консьюмеру: consumer.setMessageListener(listener);

### Уровни гарантии доставки сообщений
* надежная доставка сообщений (reliable) - система гарантирует, что в процессе обмена сообщениями ни один сетевой пакет не будет потерян;
* гарантированная доставка сообщений (guaranteed) - сообщение доставляется адресату немедленно или через заданный промежуток времени, не превышающий определенного значения (в случае, если сеть в данный момент не доступна);
* застрахованная доставка сообщений (assured) - самая строгая гарантия: каждое сообщение доставляется только один раз.

## Асинхронная обработка в jms
**JMS** обеспечивает асинхронную связь: после того, как отправитель отправил сообщение, он может продолжить другие сервисы (услуги), не блокируя и не ожидая ответа получателя. Но у получателя есть два режима приема сообщений:

* Прием сообщений синхронно: получатель активно принимает сообщения. Если в очереди сообщений нет сообщений, ожидание будет заблокировано, при этом можно указать тайм-аут или не ждать
* Прием сообщений асинхронно: при наличии сообщения в очереди будет вызван метод `onMessage` получателя, который не блокируется и может выполнять другие сервисы.

## Архитектура JMS
### Компоненты JMS
Приложение JMS состоит из следующих частей.
* **Провайдер JMS** — система обмена сообщениями, реализующая интерфейсы
JMS и предоставляющая функции администрирования и управления. Реализация
платформы Java EE, поддерживающая полный профиль, включает провайдера JMS.
* **JMS-клиенты** — программы или компоненты Java, отправляющие и получающие
сообщения, в качестве них может выступать любой компонент приложения Java EE, а также Java SE.
* **Сообщения** — объекты, передающие информацию между клиентами JMS. Состоят из заголовка (JMSDestination, JMSMessageID, JMSTimestamp...), **Свойств** - пары  ключ-значение, Тело - содержит информацию о типе сообщения (TextMessage, BytesMessage, MapMessage, ObjectMessage, StreamMessage) и полезную нагрузку.
* **Администрируемые объекты** — объекты JMS, настроенные для использования клиентами. Два вида администрируемых объектов JMS — пункты назначения и фабрики соединений — описаны в Администрируемые объекты JMS. Администратор может создавать объекты, доступные всем приложениям, использующим конкретную установку сервера GlassFish. Альтернативно, разработчик может использовать аннотации для создания объектов, специфичных для конкретного приложения.
Всего 2 вида:
  * Connection Factory - создает соединения с брокером
  * Destination - предоставление физическом очереди или топика

## Распределенная система на базе JMS
Определение JMS

**Распределенная система на базе JMS** — архитектурная модель, в которой несколько независимых приложений или компонентов (JMS-клиентов) взаимодействуют исключительно через общий брокер сообщений (JMS-провайдер), не имея прямых связей друг с другом. Такая система строится на принципах асинхронного обмена сообщениями, где отправитель и получатель разделены во времени и пространстве, а брокер берет на себя маршрутизацию, хранение и доставку сообщений, обеспечивая слабую связанность и отказоустойчивость распределенных компонентов.

### Элементы распределенной системы JMS
* **JMS-провайдер (брокер)** — ядро системы, которое может работать как отдельный сервер (ActiveMQ, Artemis, RabbitMQ с JMS-плагином). Отвечает за прием, хранение, маршрутизацию и доставку сообщений, а также управление очередями и топиками, обеспечивая единую точку интеграции для всех компонентов. Является критической точкой. что решается кластеризацией

* **JMS-клиенты** — географически или процессно распределенные компоненты (микросервисы, legacy-системы, внешние приложения), которые ничего не знают друг о друге и взаимодействуют только через брокера. Клиент может быть как отправителем (producer), так и получателем (consumer), либо совмещать обе роли.

* **Администрируемые объекты** — фабрики соединений (`ConnectionFactory`) и пункты назначения (`Destination`), которые настраиваются администратором на стороне брокера и предоставляются клиентам через JNDI, скрывая от них физические адреса, порты и протоколы подключения.

### Типы распределенных взаимодействий в JMS
* Модель **Point-to-Point** (P2P) — один отправитель отправляет сообщение в конкретную очередь, и это сообщение будет доставлено ровно одному из нескольких получателей, слушающих эту же очередь. Идеально для распределения задач между рабочими узлами (competing consumers) и балансировки нагрузки.

* Модель **Publish-Subscribe** (Pub-Sub) — один отправитель (издатель) отправляет сообщение в топик, и все активные подписчики получают его копию. Позволяет реализовать широковещательное уведомление всех заинтересованных распределенных компонентов о наступлении события.
  * Долговременная подписка (**Durable Subscription**) — специальный механизм Pub/Sub, при котором подписчик, временно отключенный от сети, не теряет сообщения: брокер сохраняет их для него и доставляет при повторном подключении. Критически важно для распределенных систем, где компоненты могут быть нестабильны или периодически отключаться.

## Cпецификация JMS
1. Основные интерфейсы API:
   1. `ConnectionFactory` -	Фабрика для создания соединений с брокером (администрируемый объект)
   2. `Destination` -	Пункт назначения: очередь (Queue) или топик (Topic)
   3. `Connection` -	Активное соединение с провайдером (создает сессии)
   4. `Session` -	Контекст для производства и потребления сообщений (однопоточный)
   5. `MessageProducer` -	Отправитель сообщений в Destination
   6. `MessageConsumer` -	Получатель сообщений из Destination
   7. `Message` -	Собственно сообщение + заголовки + свойства + тело
   8. `MessageListener` -	Интерфейс для асинхронного приема (метод onMessage())
2. Модели доставки сообщений:
   1. Point-to-Point (P2P) - используется когда нужно чтобы сообщение отправлялось только 1 потребителю и характеризуется следующим. Сообщение попадает в queue адресата и может быть прочитано когда угодно, после обработки удаляется
   2. Publish/Subscribe (Pub/Sub) - используется, когда нужно распределить сообщение по всем потребителям и характеризуется следующим. Подписчик подписывается на определённую «тему» (**topic**), могут подписывать на несколько. Издатель публикует своё сообщение, которое получают все подписчики этой темы
3. Типы сообщений: `TextMessage, BytesMessage, MapMessage, ObjectMessage, StreamMessage`
4. Структура сообщения:
   1. **Заголовок** – содержит информацию, которая используется для маршрутизации и идентификации сообщений (обязательный). Заголовок хранит мета информацию сообщения, заполняемую автоматически (JMSCorrelationID, JMSDeliveryMode, JMSDestination).
   2. **Свойство** – содержит информацию, которую можно использовать для фильтрации сообщений (время, дата и т. п.). Поле свойств схоже с заголовком, но оно заполняется программно, и позже получатель сможет прочитать эту информацию.
   3. **Тело** – содержит информацию о типе сообщения (определяется при создании сообщения) и полезную нагрузку.
5. Администрируемые объекты - объекты, которые создаются администратором (через консоль сервера) и ищутся клиентом через JNDI:
   1. `ConnectionFactory` - Инкапсулирует параметры подключения к брокеру (хост, порт, логин/пароль, пулы)
   2. `Destination` - Абстрагирует физическое имя очереди/топика от клиентского кода
