## @Scheduled

@**Scheduled** — аннотация Spring, которая позволяет превратить любой public метод Spring-бина в задачу по расписанию. Её работа строится на нескольких ключевых компонентах:
* **@EnableScheduling** — включается на уровне конфигурации (@SpringBootApplication), что активирует механизм сканирования аннотаций.
* **ScheduledAnnotationBeanPostProcessor** — бин-постпроцессор, который при старте контейнера находит все методы с @Scheduled и регистрирует их как задачи в планировщике .
* **TaskScheduler** — интерфейс планировщика. Реализация по умолчанию — `ThreadPoolTaskScheduler`, который использует пул потоков для выполнения задач. Также доступен SimpleAsyncTaskScheduler, где каждая задача выполняется в отдельном потоке (например, для virtual threads)

### Способы конфигурации
1. Фиксированный интервал - запуск с заданной периодичностью независимо от времени выполнения задачи: `@Scheduled(fixedRate = 60000) // каждые 60 секунд`
2. Фиксированная задержка - cледующий запуск начинается только после завершения предыдущего: `@Scheduled(fixedDelay = 5000) // через 5 секунд после завершения предыдущего`
3. Cron-выражение - наиболее гибкий способ: `@Scheduled(cron = "0 0 9 * * *") // каждый день в 9:00`
Spring использует расширенный синтаксис Cron Expression, добавляя 6 поле для секунд: `second(s) minute(s) hour(s) day(s) month(s) weekday(s)`

### Особенности
* По умолчанию **однопоточный**: если не настроен пул, задачи выполняются в одном потоке и длительная задача блокирует остальные
* **Не сохраняет состояние**: при перезапуске приложения все расписания пересоздаются заново, пропущенные запуски не восстанавливаются 
* **Нет кластеризации**: в кластере каждый узел запустит задачу одновременно. Для кластерной синхронизации нужно использовать ShedLock, Quartz или БД

## EJB Timer Service
**EJB Timer Service** — контейнерный сервис Jakarta EE, управляющий таймерами на уровне EJB-контейнера. **Таимеры** бывает двух типов:
* Автоматические таймеры — создаются контейнером при деплое приложения на основе аннотаций `@Schedule` или `@Schedules`
* Программные таймеры — создаются вручную через инжектированный `TimerService`; метод, вызываемый по таймеру, маркируется `@Timeout`

По умолчанию таймеры **персистентны** (сохраняются в БД): если сервер упал, а во время простоя истекло время выполнения таймера, контейнер вызовет его при старте.

### Способы конфигурации
1. Автоматические таймеры:
   1. Один таймер: `@Schedule(dayOfWeek = "Sun", hour = "0")`. Можно использовать единую строку cron, либо отдельные атрибуты аннотации (second, minute, hour, dayOfMonth, month, dayOfWekk)
   2. Несколько расписаний: 
   ```java
   @Schedules({
      @Schedule(dayOfMonth = "Last"),
      @Schedule(cron = "0 35 11 * * 1-5")
   })
   public void doPeriodicCleanup() { ... }
   ```
2. Программные таймеры
   ```java
   @Resource
   private TimerService timerService;
   // Через 1 минуту
   Timer timer = timerService.createSingleActionTimer(60000, new TimerConfig());

   @Timeout 
   public void myTimeoutMethod(Timer timer) { // метод обработчик
      System.out.println("Timer expired: " + timer.getInfo());
   }
   ```

## ScheduledExecutorService
**ScheduledExecutorService** — интерфейс из пакета `java.util.concurrent`, предназначенный для планирования выполнения задач с задержкой или периодичностью. Основная реализация - **ScheduledThreadPoolExecutor**, внутри использующий пул потоков `ThreadPoolExecutor` и специализированную блокирующую очередь `DelayedWorkQueue`, хранящую задачи в порядке времени их следующего запуска. Такая архитектура позволяет выполнять несколько задач параллельно, если в пуле более одного потока, и изолирует сбои - исключение в одной задаче не останавливает выполнение остальных. Экземпляр планировщика создается внутри приложения и управляется им напрямую: его жизненный цикл жестко привязан к жизненному циклу JVM-процесса, в котором он запущен

### Способы конфигурации
Основной способ настройки — использование фабричных методов утилитного класса `Executors`, например через `Executors.newScheduledThreadPool(int corePoolSize)`, указав желаемое количество потоков. Для более тонкой настройки (например, с пользовательской `ThreadFactory` для именования потоков или `RejectedExecutionHandler` для обработки перегрузок) можно напрямую инстанцировать `ScheduledThreadPoolExecutor`, передав параметры в его конструктор 

### Методы планирования
* Однократная задача: `schedule(Runnable command, long delay, TimeUnit unit)` — выполняет задачу **один раз** после указанной задержки
* С фиксированной скоростью: `scheduleAtFixedRate(Runnable command, long initialDelay, long period, TimeUnit unit)` — запускает задачу с постоянным интервалом между началами выполнения независимо от длительности самой задач
* С фиксированной задержкой: `scheduleWithFixedDelay(Runnable command, long initialDelay, long delay, TimeUnit unit)` — запускает задачу, выдерживая постоянную паузу между окончанием предыдущего запуска и началом следующего

Все методы возвращают объект `ScheduledFuture`, который можно использовать для отмены задачи или проверки её статуса
