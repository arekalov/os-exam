### Принципы SOA

* **Standartized Contractd** – интерфейсы взаимодействия должны быть четко
специфицированы.
* **Reference Autonomy** – взаимосвязи между сервисами должны быть сведены к
минимуму.
* **Location Transparency** – то, где физически располагается сервис, не должно иметь значения при взаимодействии с ним.
* **Longevity** – сервисы должны разрабатываться с учётом возможности их
длительного использования.
* **Abstraction** – внутренняя логика сервиса должна быть скрыта от клиента.
* **Autonomy** – сервисы должны самостоятельно контролировать собственную
функциональность.
* **Statelessness** – сервис не должен сохранять состояние между обращениями к нему.
* **Granularity** – сервис должен реализовывать чётко специфицированный и логически обоснованный набор функций.
* **Normalization** – сервисы должны быть декомпозированы и нормализованы, чтобы
минимизировать избыточность.
* **Composability** – функциональность сервиса может строиться на базе
функциональности других сервисов.
* **Discovery** – сервисы должны сопровождаться метаданными, позволяющими
эффективно идентифицировать и использовать их.
* **Reusability** – логика приложения разбивается на локальные сервисы, что позволяет повторно использовать код.
* **Encapsulation** – в сервисы можно “оборачивать”  функциональность приложений,
построенных по принципам, отличным от SOA

### Подходы к реализации SOA

1. **SOAP-ориентированный подход** - Взаимодействие сервисов осуществляется с использованием протокола SOAP
    * Обмен сообщениями в формате XML.
    * Описание интерфейсов сервисов с помощью WSDL.
    * Возможность использования различных транспортных протоколов (HTTP, SMTP и др.).
    * Поддержка дополнительных стандартов WS-* для безопасности, надёжной доставки сообщений и других функций.
2. **REST-ориентированный подход** - Взаимодействие осуществляется в соответствии с архитектурным стилем REST, обычно поверх HTTP
    *  Доступ к ресурсам через URI.
    * Использование HTTP-методов: GET, POST, PUT, PATCH, DELETE.
    * Передача данных преимущественно в JSON, также возможен XML.
    * Отсутствие состояния между запросами (Stateless).
    * Использование стандартных HTTP-кодов состояния.
3. **Взаимодействие через системы обмена сообщениями** - Сервисы обмениваются сообщениями через промежуточное ПО — **брокер сообщений** (RabbitMQ, Apache Kafka, ActiveMQ).
     * Сервисы не обязательно взаимодействуют напрямую.
     * Отправитель помещает сообщение в очередь или публикует его в канал.
     * Получатель забирает сообщение и обрабатывает его.
     * Возможна асинхронная обработка запросов.
     * Снижается зависимость сервисов от доступности друг друга в конкретный момент времени.

4. Использование **ESB (Enterprise Service Bus)** — корпоративная сервисная шина, обеспечивающая взаимодействие и интеграцию различных сервисов в SOA.
    Основные функции ESB:
    - Маршрутизация сообщений между сервисами.
    - Преобразование форматов данных.
    - Преобразование протоколов.
    - Обработка сообщений и ошибок.
    - Интеграция систем, использующих разные технологии.
5. WCF (by M$).
6. Apache Thrift.
7. gRPC (by Google).

### Основные стандарты и протоколы SOA
* **SOAP (Simple Object Access Protocol)** - Протокол обмена структурированными сообщениями между сервисами.
  - Использует XML для представления сообщений.
  - Определяет структуру SOAP-сообщения.
  - Может работать поверх HTTP и других транспортных протоколов.
  - Поддерживает расширения WS-*.
* REST (Representational State Transfer) - Архитектурный стиль построения распределённых систем, а не протокол.
  - Обычно использует HTTP.
  - Работает с ресурсами, идентифицируемыми через URI.
  - Использует стандартные HTTP-методы.
  - Часто использует JSON для передачи данных.
* WSDL (Web Services Description Language) - Язык описания веб-сервисов, преимущественно SOAP-сервисов. Определяет:
  - Какие операции предоставляет сервис.
  - Какие сообщения он принимает и возвращает.
  - Форматы данных.
  - Способ и адрес взаимодействия с сервисом.
* XML (Extensible Markup Language) - Расширяемый язык разметки, используемый для структурированного представления и обмена данными.
  - Имеет иерархическую структуру.
  - Использует пользовательские теги.
  - Поддерживает проверку структуры с помощью XML Schema (XSD).
  - Используется в SOAP-сообщениях и WSDL-документах.
- HTTP (HyperText Transfer Protocol) - Протокол прикладного уровня, обеспечивающий передачу данных между клиентом и сервером. В контексте SOA:
  - Используется для передачи SOAP-сообщений.
  - Является основой большинства RESTful-сервисов.
  - Определяет методы запросов, заголовки и коды состояния.
  - Может использоваться совместно с TLS для защиты передаваемых данных (HTTPS).

### Роль сервисов и сервисных контрактов в SOA

**Сервисы** - основными строительными блоками SOA. Каждый сервис предоставляет определённую бизнес-функцию и может использоваться другими сервисами или приложениями. Основные роли сервисов:
- **Инкапсуляция бизнес-логики** — каждый сервис отвечает за определённую функциональность.
- **Повторное использование** — один сервис может использоваться несколькими приложениями.
- **Интеграция** — сервисы позволяют объединять функциональность различных систем.
- **Декомпозиция приложения** — сложное приложение разделяется на независимые компоненты.
- **Гибкость** — сервисы можно изменять и развивать независимо друг от друга при сохранении совместимости интерфейсов.

**Сервисный контракт** — формальное описание интерфейса сервиса и правил взаимодействия с ним, включает в себя предоставляемые операции, входные и выходные параметры, формат сообщений и протокол взаимодействия, а также требования к нему (авторизация), обеспечивает:
* Независимость потребителя от внутренней реализации сервиса.
* Возможность разрабатывать сервисы независимо друг от друга.
* Совместимость сервисов, реализованных на разных платформах.
* Упрощение интеграции и тестирования.
* Возможность автоматической генерации клиентского кода и документации.
