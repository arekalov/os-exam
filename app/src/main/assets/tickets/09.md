### Понятие REST.

**REST** (Representational State Transfer) — архитектурный стиль построения распределённых систем, предложенный Роем Филдингом, определяет набор архитектурных ограничений, которым должна соответствовать система для обеспечения масштабируемости, простоты взаимодействия и независимости компонентов. REST обычно использует HTTP как протокол взаимодействия, а данные передаются в виде представлений ресурсов, чаще всего JSON. **RESTful-веб-сервис** — веб-сервис, построенный с соблюдением архитектурных принципов REST.

**Основная идея REST**: система представляется в виде набора ресурсов, с которыми клиент взаимодействует посредством стандартного интерфейса.

**Ресурс** — любой объект или сущность системы, доступная для взаимодействия через API, имеет уникальный идентификатор — **URI**

### Основные архитектурные ограничения REST
REST определяется 6 основными архитектурными ограничениями:
1. Client-Server — клиент-серверная архитектура.
2. Stateless — отсутствие состояния взаимодействия на сервере.
3. Cacheability — возможность кэширования.
4. Uniform Interface — единый интерфейс.
5. Layered System — многоуровневая система.
6. Code on Demand — передача исполняемого кода клиенту (необязательное ограничение).

### Клиент-серверная архитектура (Client-Server)
**Client-Server** — ограничение, согласно которому система разделяется на 2 независимые стороны, взаимодействующие через стандартизированный интерфейс:
- Клиент — отправляет запросы, получает данные и отвечает за пользовательский интерфейс.
- Сервер — хранит и обрабатывает данные, выполняет бизнес-логику и предоставляет API.

Основная **задача** разделения — независимое развитие клиента и сервера. Также позволяет упростить разработку и сопровождение и масштабировать серверную инфраструктуру отдельно от клиентов


### Stateless — отсутствие состояния
**Stateless** — архитектурное ограничение, согласно которому каждый запрос клиента должен содержать всю информацию, необходимую серверу для его обработки. Сервер не должен полагаться на сохранённый контекст предыдущих запросов конкретного клиента.
**Преимущества**: упрощается масштабирование и восстановление сервера, поскольку запросы независимы друг от друга и могут обрабатываться разными экземплярами.
**Недостатки**: клиенту необходимо передавать все необходимые данные с каждым запросом, что увеличивает объём трафика и может усложнять клиентскую логику.

### Cacheability — возможность кэширования
**Cacheability** — ограничение, согласно которому ответы сервера должны явно указывать, можно ли их кэшировать и в течение какого времени. Для управления кэшированием HTTP использует специальные **заголовки** (Cache-Control, 
ETag, Expires, Last-Modified)

Позволяет уменьшить количество запросов к серверу и снизить сетевую нагрузку, однако при неправильной настройке кэширования клиент может получить устаревшие данные.

### Uniform Interface — единый интерфейс
**Uniform Interface** — ограничение, согласно которому взаимодействие клиента и сервера должно осуществляться через единый стандартизированный интерфейс, обеспечивает независимость компонентов. Выделяют 4 составляющие:
1. **Идентификация ресурсов** - Каждый ресурс должен иметь уникальный идентификатор, обычно URI.
2. **Манипуляция ресурсами через представления** - Клиент получает представление ресурса, изменяет его и отправляет серверу для обновления (PUT/PATCH).
3. **Самоописываемые сообщения** - Сообщения должны содержать достаточно информации для понимания способа их обработки. Например, заголовок Content-Type или HTTP-код
4. HATEOAS - Ответ сервера может содержать ссылки на связанные ресурсы и доступные следующие действия.

### Layered System — многоуровневая система
**Layered System** — ограничение, согласно которому архитектура может состоять из нескольких промежуточных уровней, через которые проходят запросы и ответы. Клиенту необязательно знать, с каким именно сервером он взаимодействует: запрос может проходить через прокси-сервер, балансировщик нагрузки, шлюз API или другие компоненты.

### Code on Demand — передача исполняемого кода
**Code on Demand** — необязательное архитектурное ограничение REST, позволяющее серверу передавать клиенту исполняемый код, который клиент может выполнить. Основная идея — динамическое расширение функциональности клиента за счёт кода, полученного от сервера. Пример: веб-сервер передаёт браузеру JavaScript-файл, который добавляет интерактивность веб-странице.

### Отличия REST от SOAP

| Критерий	| REST	| SOAP| 
|----|---|---|
| Тип	| Архитектурный стиль	| Протокол| 
Основная концепция	| Работа с ресурсами	| Обмен структурированными сообщениями| 
| Формат данных	| JSON, XML и другие	| XML| 
| Транспорт	| Обычно HTTP/HTTPS| 	HTTP, SMTP и другие| 
Интерфейс	| URI и HTTP-методы	| Операции и SOAP-сообщения| 
| Описание интерфейса	| Часто OpenAPI	| Обычно WSDL| 
| Структура сообщений	| Определяется HTTP и представлением ресурса	| Строго заданная структура Envelope, Header, Body| 
| Состояние	| Stateless — обязательное ограничение REST	| Зависит от реализации| 
| Кэширование	| Поддерживается средствами HTTP| 	Не является встроенным архитектурным требованием SOAP| 
| Безопасность	| TLS, OAuth 2.0, токены и другие механизмы	| TLS, WS-Security и другие WS-*| 
| Сложность| 	Обычно проще	| Обычно сложнее| 
| Типичное применение| 	Веб- и мобильные API	| Корпоративные интеграции|
