## Восстановление данных в PostgreSQL

PostgreSQL использует WAL (Write-Ahead Logging) — журнал предзаписи. Принцип: любое изменение данных сначала записывается в WAL на диск, и только потом — в основные файлы данных. Это гарантирует durability при сбоях.

Точки восстановления:
* Контрольные точки (Checkpoint) — периодическая запись всех грязных буферов на диск. Сокращают время восстановления: redo нужно применять только с последней контрольной точки.
* PITR (Point-In-Time Recovery) — восстановление на любой момент времени с помощью архива WAL-файлов и базовой резервной копии.

**Алгоритм восстановления** PostgreSQL — основан на ARIES, но с упрощениями: использует `pg_control` для отслеживания состояния, а фаза Analysis встроена в процесс старта.

### steal/no-steal, force/no-force
Это политики управления буферным пулом — определяют, когда изменённые страницы записываются на диск.

**steal / no-steal** — может ли менеджер буферов вытолкнуть на диск «грязную» (изменённую незафиксированной транзакцией) страницу:
* **steal** — да, можно вытеснить незафиксированные изменения. Нужен UNDO-журнал для отката.
* **no-steal** — нет, грязные страницы незафиксированных транзакций не записываются. Не нужен UNDO, но требует больше памяти.

**force / no-force** — должны ли все изменённые страницы транзакции быть записаны на диск до COMMIT:
* **force** — при COMMIT все грязные страницы транзакции сбрасываются на диск. Не нужен REDO, но медленный COMMIT.
* **no-force** — при COMMIT страницы могут оставаться в буфере. Нужен REDO-журнал для восстановления после сбоя.

PostgreSQL использует **steal + no-force** — наиболее производительная комбинация, требующая и UNDO, и REDO (реализовано через WAL).

## ARIES
**ARIES** (Algorithm for Recovery and Isolation Exploiting Semantics) — стандартный алгоритм восстановления после сбоев, используемый в большинстве СУБД. Основан на WAL: любое изменение данных сначала пишется в журнал.

### Три фазы восстановления
* **Analysis (анализ)** — сканирование журнала с последней контрольной точки (checkpoint) для определения: какие транзакции были активны в момент сбоя, какие страницы могут быть «грязными».
* **Redo (повтор)** — повтор всех операций из журнала начиная с нужной точки, чтобы привести базу к состоянию на момент сбоя. Повторяются даже операции незафиксированных транзакций.
* **Undo (откат)** — откат всех незафиксированных на момент сбоя транзакций в обратном порядке. Каждая операция отката тоже пишется в журнал (Compensation Log Records, CLR) — защита от повторного сбоя во время восстановления.

Принцип: **«история повторяется, затем откатывается»** — сначала база возвращается в точное состояние момента сбоя (redo), затем убираются незавершённые транзакции (undo).
